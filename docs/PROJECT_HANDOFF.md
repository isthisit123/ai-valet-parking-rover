## 1. 전체 프로젝트 개요

### 1.1 프로젝트 목표

**Arduino UNO Q 기반 Q-ROVER를 이용한 AI 발렛파킹 모형 시스템**을 구현한다.

- 천장 또는 모서리에 설치한 고정 카메라로 모형 주차장 전체를 관찰한다.
- 미리 정의된 지도 이미지의 도로/주차칸/건물/입구/출구를 분석하고, 도로를 **가중치 그래프**로 변환한다.
- 사용자의 주차 조건(출구와 가까운 곳, 건물 A/B와 가까운 곳 등)에 맞는 **이용 가능한 주차칸**을 선택한다.
- 해당 주차칸까지 **다익스트라 최단 경로**를 계산하고, 경로를 시각화하며, 로버 제어 모듈에 경로 좌표를 전달한다.
- 다른 팀원의 YOLO 모듈이 감지한 점유 상태를 반영하여 이미 차가 있는 주차칸을 선택하지 않게 한다.
- 로버 상단 **ArUco 마커**와 천장 카메라를 사용해 로버의 위치/방향 `(x, y, θ)`를 추적한다.
- 실제 모형의 카메라 보정과 좌표 변환 후 로버가 경로를 주행하고 목적지에 도착했는지 판단한다.

### 1.3 현재 지도 인식 방식과 한계

- **학습된 AI 모델이 아니다.** OpenCV 기반 색상 분리 및 연결 영역 분석을 활용한다.
- 지도 이미지 제작 규칙: **도로=빨간색**, **일반 주차칸=흰색 바탕에 P**, **장애인 주차칸=파란색 바탕에 P**, **건물=짙은/검은색 사각형**, **입구·출구=회색 네모**. 배경과 기타 표시가 HSV 마스크에 섞이지 않도록 규칙을 유지한다.
- 건물 **A/B**의 고유 명칭, 회색 출입구의 **entrance/exit** 구분은 현재 **지도별 힌트 좌표를 수동 입력**한 설정값으로 연결한다. 검출된 영역 자체는 OpenCV로 찾는다.
- 다른 지도로 옮겨도 같은 규칙이라면 처리 가능하도록 만드는 것이 목표. 아직 **지도 2종**에서 검증한 것이며, 복잡한 교차점·루프·곡선·대각선·다중 연결 컴포넌트에 대한 일반화는 확정되지 않았다.

## 3. 구현된 데이터 처리 파이프라인

```text
[parking_map_v1.png]

       v

       |

       |

 - 현재는 콘솔에 선택 노드/경로/거리 출력
```

### 3.1 그래프 처리의 핵심 알고리즘

- **HSV Color Segmentation**: 빨간색 중심선 도로 영역 추출(색상 랩어라운드 포함).
- **Connected Components**: 작은 빨간 범례/잡음을 제거하고 건물·주차칸·게이트 영역을 개별 검출.
- **Skeletonization (scikit-image)**: 폭이 있는 도로를 가는 중심선으로 변환.
- **8-neighbor analysis**: 인접 스켈레톤 픽셀 수 1이면 끝점, 3개 이상이면 교차점 후보. 교차점은 근접한 후보를 하나로 병합.
- **NetworkX pixel graph**: 각 중심선 픽셀을 노드로 사용, 수평/수직은 길이 1, 대각은 `sqrt(2)`; 대각선 지름길 방지 처리.
- **Connected Components + Shortest Path**: 최종 그래프의 노드 주변을 제외하고 도로 구간을 분리한 뒤, 구간별 픽셀 경로와 길이를 복원.
- **Weighted MultiGraph**: 서로 같은 두 노드에 복수 간선이 생길 수 있도록 자료구조를 사용하되 **현행 구현이 모든 고리/루프를 안전하게 처리한다고 가정하면 안 됨**.
- **Dijkstra**: 시설 조건에 맞게 주차 후보를 평가하고, 입구부터 선택 주차칸까지 최단 경로를 구함.

### 3.2 데이터 예시 및 주의점

```json
{
  "unit": "pixel",
  "nodes": [
    {"id": "N4", "type": "endpoint", "x": 906, "y": 696}
  ],
  "edges": [
    {
      "from": "N4",
      "to": "N10",
      "weight": 220.0,
      "path": [[906, 696], [900, 696], [899, 696]]
    }
  ]
}
```

> 위 예시는 **이해를 위한 발췌**이다. 실제 노드/간선의 전체 배열 및 `path`에는 다수의 중간 좌표가 저장된다. 특히 기존 지도 1에서 N4가 입구였지만, 지도 2에서는 N3가 입구였다. **N번호에 의미를 하드코딩하면 안 되고 `role` 또는 시설 ID를 사용**해야 한다.

- `weight`: 도로 중심선을 따라 계산한 **픽셀 단위 길이**.
- `path`: 해당 간선을 따라 이동하는 순서 있는 `[x, y]` 픽셀 좌표(도착 로버 제어 명령이 아님).
- `type`: 그래프 구조상의 `endpoint`/`junction`.
- `role`: 의미상의 `parking_normal`, `parking_accessible`, `entrance`, `exit` 등.
- 건물은 도로 끝점이 아니라 **별도 영역(사각형/bbox)**으로 표현.
- 그래프 `N0` 등의 ID는 지도 변경 시 달라질 수 있다. 주차칸 고유 ID `P1`, `P2` 등을 **노드 ID와 분리**하는 개선이 필요하다.

### 3.3 주차 조건의 현재 의미

| preference | 선택 기준 | 주의 |
|---|---|---|
| `entrance` | 입구 노드까지 그래프 도로 최단 거리 | 첫 번째 지도에서 동작 검증 |
| `exit` | 출구 노드까지 그래프 도로 최단 거리 | 입구→주차칸 경로와는 점수가 다를 수 있음 |
| `building_a` | 주차칸과 건물 A의 이미지상 **직선거리** | 실제 건물 출입문까지의 보행 거리가 아님 |
| `building_b` | 주차칸과 건물 B의 이미지상 **직선거리** | 실제 보행로/장애물 고려 전 |

- 현재는 **모든 일반 주차칸이 비어 있다고 가정**한 시연 방식이었다. 점유 정보는 YOLO 팀원과 통합할 때 연결.
- 장애인 주차칸은 **기본 후보에서 제외**하고, 적격 사용자에게 허용되는 별도 옵션으로 취급해야 한다.
- 일부 코드 버전은 `occupied_ids`/`allow_accessible` 매개변수를 이미 가지고 있을 수 있다. 실제 로컬 정의를 점검할 것.

## 4. 실행 명령어와 검증된 결과

### 4.1 실행 순서 (프로젝트 루트, PowerShell)

```powershell
# VS Code에서 이미 (.venv)가 활성화된 경우
py -m src.map_processing.graph_exporter
py -m src.map_processing.semantic_mapper
py -m src.map_processing.parking_selector
```

또는 가상환경 Python으로 `python -m ...`을 사용한다. `map_reader.py`와 `graph_builder.py`는 주로 다른 모듈이 함수를 import하여 사용하므로 별도 실행은 필수가 아니다.

- `graph_exporter`: `data/graphs/parking_map_v1.json`, `graph_preview.png`

- `parking_selector`: 콘솔에 조건별 선택 주차칸, 점수, 출발지~주차칸 최단 노드 경로, 도로거리 출력

## 5. 확정된 개발 순서 및 완료 조건

### 단계 1 — **다른 지도 검증: 완료(기본 2종)**

- 도로 마스크 → 중심선 → 끝점/교차점 → 그래프 → JSON
- 주차칸/건물/출입구 의미 부여
- 조건별 주차 선택 및 다익스트라 실행
- **남은 유의점:** 완전한 자동 일반화는 아님. 사용자가 정한 색상 규칙과 지도별 힌트가 필요.

### 단계 2 — **코드 리팩토링: 다음 작업**

**시점:** 다른 지도 기본 검증을 마쳤으므로, **경로 시각화를 구현하기 전에** 실시한다.

**목표:** 기능을 추가할수록 파일 하나가 비대해지는 문제를 해결하고, 새 지도를 쉽게 지정하며, 팀원과 연동할 명확한 API/데이터 계약을 만든다.

제안 작업:

1. **현상 파악:** Git 상태, 의존성, 실제 함수/호출 관계, 입출력 JSON 스키마, 중복/죽은 코드 식별.
2. **회귀 테스트 추가:** 원본 지도 결과(노드 12/간선 11, 의미 매핑, 4개 preference 경로) 및 두 번째 지도 결과를 가능한 한 fixture로 보존. 파일 덮어쓰기 없이 `pytest` 또는 간단한 검증 스크립트로 비교할 수 있게 정리.
3. **지도 선택/경로 설정 분리:** `IMAGE_PATH`, `parking_map_v1` 문자열, 출력 경로, 색상값, 영역/교차점 크기 등 하드코딩된 값을 한곳에서 관리. **서로 다른 map_id를 병행 테스트**할 수 있도록 구성.
4. **모듈별 책임 정리:** I/O(파일), 도로 검출, 그래프 구성, 시설 검출/라벨 매핑, 주차 선택, 경로 계획을 분리. 유사한 기능의 중복 함수 제거.
5. **데이터 스키마 정리:** `map_id`, `unit`, `coordinate_system`, `nodes`, `edges`, `parking_spaces`, `landmarks` 등의 공통 규약 확정. 단 기존 파일과의 하위 호환 및 단계별 마이그레이션 고려.
6. **명시적 오류 처리:** 건물/출입구 검출 실패, 고유 ID 중복, 매핑되지 않은 주차칸, 그래프 끊김, 불가능한 경로 등 원인을 알려주는 오류 메시지.
7. **품질 검사:** 경로 방향 불변식, 간선 길이, 노드 연결, 시설 수량/ID, 경로 도달 가능성, `git diff` 확인.

### 단계 3 — **최단 경로 시각화: 미구현**

**목표:** `parking_selector` 결과(노드 순서)를 사용하여 원본 지도에 **실제 도로 중심선을 따른 경로**를 색으로 표시. 동시에 로버 제어 팀에 전달할 **연속 waypoints**를 생성.

- 각 노드 쌍의 선택된 그래프 간선에서 `path` 좌표를 읽는다.
- `path`가 목표 이동 방향과 반대면 역순으로 뒤집는다.
- 인접 간선 사이 중복 노드 좌표 제거, waypoint 연결 상태/도약 거리 검사.
- 복수 간선(MultiGraph)이 있을 수 있으므로 노드 쌍만이 아니라 **다익스트라가 선택한 최소 비용 간선**과 해당 `path`를 정확히 매칭한다.
- 경로에 입구/목적지/교차점, 길이 및 지도 선택 조건을 표시한다.
- 출력 예시: `data/graphs/<map_id>_route.png`, `data/graphs/<map_id>_route.json`.
- 현재 스켈레톤의 노드 영역 처리 때문에 간선 끝에 수~수십 픽셀 길이의 경로 점프가 있을 수 있다. **시각화 및 연속성 검사로 확인/보정**한다.

**완료 조건:** 모든 기존 조건(`entrance`, `exit`, `building_a`, `building_b`)에 대해 선택된 주차칸까지 도로를 따라 강조 표시되며, 원본 지도와 JSON waypoint의 좌표가 일치한다.

### 단계 4 — **실물 제작 후 카메라 캘리브레이션: 미구현**

- 모형 주차장 실측 크기, 카메라 위치, 렌즈/해상도 확정.
- 체커보드 등으로 카메라 내부 파라미터 및 왜곡 계수 추정 후 렌즈 왜곡 보정.
- 천장 카메라 영상에서 기준점(가능하면 4개 이상, 충분히 넓게 분포)을 측정.
- 카메라가 정면이 아닌 모서리에 있어도 바닥 평면을 기준으로 원근 변환할 수 있게 준비.
- **주의:** ArUco 마커가 로버 위에 있는 경우 바닥과의 높이 차이, 마커 중심↔로버 중심 위치/방향 오프셋을 별도 보정해야 함.

### 단계 5 — **월드 좌표계 및 Homography: 미구현**

- 실제 모형의 원점, +x, +y 방향, 단위(cm 또는 m) 정의. 예: 왼쪽 아래 `(0,0)`, 오른쪽 +x, 위쪽 +y.
- 지도 이미지 픽셀→월드와 천장 카메라 픽셀→월드의 **각기 다른 변환**을 올바르게 계산한다.
- OpenCV `getPerspectiveTransform`/`findHomography` 및 `perspectiveTransform` 활용 가능.
- 원본 지도 노드/간선 `path`를 실제 좌표계로 변환하고 **월드 좌표상 간선 길이를 재계산**한다.
- 로버 `(x,y,θ)` 추정, waypoint 추종 및 도착 허용오차 계산용 공통 좌표 규약 마련.
- 원근 보정은 바닥 평면에 적용되므로 위쪽에 설치된 ArUco의 높이/시차를 무시하지 말 것.

### 단계 6 — **다른 팀 모듈과 통합: 향후 협업**

- YOLO 팀: 각 `parking_space_id`에 대한 `occupied`/`free` 결과와 신뢰도/타임스탬프 반환.
- 경로 선택 모듈: 점유된 주차칸 필터링, 장애인 공간 기본 제외, 주차 조건으로 목적지 결정, 최단 경로/waypoints 출력.
- 로버 제어 팀: 월드 좌표 waypoint와 로버 현재 위치/방향을 받아 제어. Arduino UNO Q/Q-ROVER 모터, 엔코더 사용 여부 확인 후 PID, 전방 ToF 센서 안전 정지, 경로/도착 판정 구현.
- 노트북 로컬 호스트에서 OpenCV/경로 탐색/FastAPI 등을 맡고 같은 Wi-Fi를 통해 로버와 통신하는 구성을 우선 고려(클라우드 GCP는 필요성 검토 후).
- **LLM/VLM은 마지막 선택 확장:** 자연어 → 구조화 주차 조건 파싱; OCR/VLM → 지도 텍스트 의미; segmentation 학습 → 자유로운 지도 색상/표현에 대한 일반화. 현재 핵심 작업에 끼워 넣지 말 것.

## 6. 향후 팀 간 데이터 계약(초안 — 실제 코드에 맞춰 협의)

아래 JSON은 **신규 표준으로 확정된 스키마가 아니라 합의용 제안**이다. 유효한 로컬 스키마를 먼저 확인하고 버전 호환 방식을 정할 것.

### 6.1 주차칸 의미 데이터

```json
{
  "parking_space_id": "P1",
  "graph_node_id": "N2",
  "type": "normal",
  "polygon_px": [[300, 250], [380, 250], [380, 380], [300, 380]]
}
```

- 고유 주차칸 ID `P1`은 지도 내 장소의 고정 식별자이며, 변경될 수 있는 그래프 노드 ID와 분리한다.
- 간단한 초기 구현은 `bbox` 사용 가능. 실제 물체 점유 판단 시 bbox 또는 polygon으로 YOLO 검출 결과와 공간 겹침을 계산한다.

### 6.2 다른 팀원의 YOLO 점유 상태 인터페이스

```json
{
  "map_id": "parking_map_v1",
  "spaces": [
    {"parking_space_id": "P1", "occupied": true},
    {"parking_space_id": "P2", "occupied": false}
  ]
}
```

- 추후 타임스탬프, 신뢰도 및 감지 실패(`unknown`)를 별도 상태로 추가하는 게 좋다.
- 확인되지 않은 상태를 빈자리로 자동 간주하지 않는 정책 권장.

### 6.3 경로 계획 출력 인터페이스

```json
{
  "map_id": "parking_map_v1",
  "start_node_id": "N4",
  "destination_parking_space_id": "P2",
  "destination_node_id": "N7",
  "node_route": ["N4", "N10", "N11", "N7"],
  "waypoints": [[906, 696], [900, 696]],
  "total_distance": 791.66,
  "unit": "pixel"
}
```

> 경로와 좌표 배열은 **예시 일부 발췌**이다. 상용/실물 제어에 사용할 때는 **전체 waypoint 배열**이 필요하고, 실물에서는 `unit: "cm"` 또는 `"m"` 및 좌표 프레임 정보가 필수다.

## 7. 알려진 기술 리스크 및 검증 사항

1. **지도 형식 의존성:** HSV 색상 경계, 밝기, 글씨/테두리, 박스 크기 때문에 잘못된 영역이 다수 검출될 수 있음. 과거에는 `Normal 9`, `Accessible 5`, `Buildings 7`, `Gates 3`으로 과다 검출되어 `ValueError: Some regions could not be assigned to nodes`가 발생했고, 이후 로컬 수정으로 `4/2/2/2` 해결됨.
2. **교차점 병합:** `31×31` 팽창/근접 픽셀 묶기 방식은 복잡한 지도에서 별개 교차점까지 병합할 수 있음. 파라미터 분리 및 테스트가 필요.
3. **단일 도로 컴포넌트:** 현재 빨간 도로에서 가장 큰 연결 컴포넌트를 채택하는 방식이라 분리된 도로 네트워크나 범례가 섞인 지도는 별도 로직 필요.
4. **순환 경로/짧은 간선:** 노드 영역을 제거한 도로 컴포넌트가 정확히 두 노드에 닿는다는 현행 가정은 고리/매우 짧은 분기/밀집 교차점에서 깨질 수 있음.
5. **대각선/곡선:** 이론적으로 픽셀 경로가 지원하나 새 지도 2종 검증만으로 다양한 기하 구조를 보장할 수 없음.
6. **path 방향:** 간선 `from→to`와 `path[0]→path[-1]`의 방향을 유지하고 역방향 주행 시에만 뒤집을 것.
7. **경로의 픽셀 도약:** 노드 주변 클러스터/근접 영역 때문에 연속 픽셀 사이에 수~수십 픽셀 점프가 있을 수 있음. 시각화 및 실제 제어 전 보정.
8. **장애물/통로 폭:** 중심선 최단 경로는 통로 폭·로버 크기·회전반경·후진/주차 자세를 고려하지 않음. 실제 주행과 주차 기동을 별도 설계.
9. **건물 거리 평가:** 현재 건물은 사각형 경계까지 직선거리 기준; 실제 출입구와 보행로 기반 평가로 확장 가능.
10. **출입구/건물 힌트 수동 입력:** 완전 자동 인식 아님. 색상 기반 검출 후 위치 설정을 사용하므로 지도 변경 시 라벨 힌트 일치 필수.
11. **장애인 주차칸 정책:** 기본 배제; 적격 조건 명시 없이 일반 추천에 포함하지 않음.
12. **Git 충돌/로컬 작업 유실:** Codex는 작업 시작 전 `git status`, `git branch --show-current`, `git diff` 확인. 임의 `git reset --hard`, 자동 force-push, 무검토 전체 리네임 금지.
